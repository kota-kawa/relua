# ADR-0022: サイトマップを上限超過でインデックス分割する

- Status: Accepted
- Scope: `frontend/lib/sitemap.ts`、`frontend/app/sitemap.xml/route.ts`、`frontend/app/sitemaps/[page]/route.ts`
- Amends: [ADR-0016](./0016-seo-outage-resilience-and-reviewed-facets.md)

## Context

ADR-0016 は、サイトマップの部分失敗を 503 と `Retry-After` で答えると定めた。これはAPI障害に対する判断としては今も有効である。

一方で、生成されるサイトマップは静的ページ・カテゴリ・企業・募集の全URLを1ファイルに連結しており、件数の上限確認もインデックス生成も無かった。サイトマップの仕様は50,000 URL（または50MB）を超えたファイルを、上限までを採用して残りを捨てるのではなく**丸ごと拒否する**。つまり在庫が閾値を越えた時点で、サイトマップは無言で無効になる。

`force-dynamic` かつ成功時に `Cache-Control` が無く、全ページ走査を `Promise.all` で一斉に投げていた点も重なっていた。未認証の誰でも `/sitemap.xml` を連打するだけで内部APIへ大量の同時リクエストを発生させられた。

## Decision

- 生成結果を `SITEMAP_CHUNK_SIZE`（45,000件）で分割する。上限の50,000に対して余裕を残すのは、仕様の上限がファイルとして配信された状態に対するもので、50MB制限がURL数より先に効く場合があるためである。
- **1ファイルに収まる間は従来どおり単一の `urlset` を返す**。上限を超えたときだけ同じ `/sitemap.xml` がサイトマップインデックスになり、子サイトマップを `/sitemaps/N.xml` で配信する。`robots.txt` が指すURLは変わらない。
- 子サイトマップは毎回データセット全体を再計算して自分のページを切り出す。分割結果をプロセス内にキャッシュすると、2つの子が別々のスナップショットから答えてページ境界が食い違い、URLがインデックスから抜け落ちる。繰り返しのファンアウトは共有キャッシュヘッダで抑える。
- `/sitemap.xml` と子サイトマップの成功応答に `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400` を付け、全ページ走査の並列数に上限を設ける。
- インデックスに収まらない規模（子サイトマップが50,000本を超える＝20億URL超）でだけ例外を投げ、ADR-0016 の 503 経路に落とす。到達しない想定だが、黙って壊れた文書を配るよりは失敗を可視化する。

## Consequences

在庫が45,000 URLを越えても、サイトマップは有効なまま配信され続ける。閾値を越えた瞬間に `/sitemap.xml` の中身が `urlset` から `sitemapindex` に変わるが、どちらも検索エンジンが解釈できる形式であり、`robots.txt` の参照先を変更する必要はない。

分割後は1回のクロールで消費されるリクエストが増える（インデックス1回＋子N回）。いずれも共有キャッシュが効くため、オリジンのファンアウトは増えない。

ADR-0016 の 503 による障害時の扱いは変更しない。
