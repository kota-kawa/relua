# ADR-0025: 企業プロフィールを企業ごとの結果付きで一括更新する

- Status: Accepted
- Scope: MCPの企業プロフィール更新契約

## Context

定期実行で多数の企業プロフィールを整備すると、企業ごとの確認と更新が外部AIクライアントのツール呼び出し上限を消費する。全社の説明を準備してから保存すると、保存前に停止する可能性がある。途中エラーの報告だけでは、一部の企業が既に保存されているか判断できない。

## Decision

- `update_company_profiles` は1〜50社を1回で受け取り、各社を個別に検証・保存する。各社に固有の `request_id` と公式ページの `source_url` を要求し、既存の文字数・自由記述・URL検証を再利用する。
- 各社の `expected_updated_at` を必須とし、企業行のロック取得後に照合する。プロフィールを変更した場合は、更新日時を必ず前回より進める。同じ内容の再試行は日時の照合前に冪等記録で解決する。
- 個別の入力不備・更新競合・対象不明はその企業だけ拒否する。予期しないエラーは共通例外境界で本文を隠し、保存結果未確認として返す。他社の成功分を保持する。
- 応答は入力順の個別結果と、成功・変更・再試行・拒否・結果未確認の件数を返す。成功数は変更なしと処理済みの再試行も含む。結果未確認は未保存と断定しない。
- 未整備企業一覧のID・現在値・公式サイトURL・更新日時を再利用し、名称の再解決を要求しない。変更履歴は過去の変更理由や出典を確認する必要がある場合に使う。
- 従来の単件更新契約は維持する。一括更新は各社の既存の冪等記録・監査ログを使い、新しいテーブルやジョブ、下書き保存機構は追加しない。

## Consequences

50社分のプロフィール保存を1回のMCP呼び出しにまとめられる。準備済みの少数社からの保存も可能で、部分失敗時の成功分を保持できる。再送するには各社の入力と `request_id` を保持する必要がある。

外部クライアントによる公式ページの調査と、その実行上限は引き続きクライアント側にある。一括更新全体は単一トランザクションではない。応答を受け取れなくても一部が保存済みの場合があるため、同じ内容で再試行して照合する。
