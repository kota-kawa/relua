# ADR-0018: 期限切れSEOスナップショットをブロッキング再取得に置き換える

- Status: Accepted
- Scope: 一覧・募集詳細・企業ページのSSRスナップショット、内部API読み取りの再試行
- Amends: [ADR-0016](./0016-seo-outage-resilience-and-reviewed-facets.md)

## Context

ADR-0016は「最後の正常取得から1時間を超えたスナップショットは利用しない」を採用し、`frontend/lib/seo-data.ts` の `assertFresh()` が期限超過で例外を投げていた。この判断はAPI障害時に古い画面を配り続けないために今も有効である。

しかしNext.js 16のData Cache（`unstable_cache`）は、`revalidate` を過ぎたエントリを通常の動的レンダリングでは**そのまま返し、更新は背後で実行する**。Data Cacheのfetchエントリは期限で消えず、再検証時刻の判定だけが行われる。そのため1時間以上アクセスがなかったURLでは、APIが完全に正常でも次の経路をたどっていた。

1. 期限切れエントリがそのまま返る。
2. `assertFresh()` が例外を投げ、HTTP 500（`This page couldn’t load`）になる。
3. 背後の再検証が完了し、Data Cacheが新しい値に入れ替わる。
4. リロードすると正常に表示される。

本番ビルドで、保存済みスナップショットの `fetchedAt` とキャッシュファイルのmtimeを4時間前へ戻すと、一覧・募集詳細・企業ページのいずれも初回500・再訪200を再現できた。検索エンジン経由に固有の不具合ではなく、**1時間以上訪問がなかったURLの最初の1リクエスト**で起きる。ロングテールURLに最初に到達するのが検索流入であるため、Google経由で目立っていた。

## Decision

- 期限超過のスナップショットは「利用しない」を維持したまま、**即時に例外を投げず最新データの取得完了を待つ**。取得できればそれを表示し、取得にも失敗した場合だけエラーを伝播させる。60秒以内はキャッシュ、60秒超〜1時間以内はキャッシュを返して背後で更新、という既存の段階は変えない。
- ブロッキング再取得は、Data Cacheが同じキーで実行中の再検証に**相乗りする**。`unstable_cache` のコールバック自体をプロセス内の in-flight マップ（`sharedSnapshot`）経由にすることで、待ち合わせた値がそのままData Cacheへ保存され、後続リクエストは再取得なしに新しい値を読む。
- 同じマップが同一キーへの同時アクセスもまとめる。`unstable_cache` の再検証重複排除は1リクエスト内にしか効かないため、これがないと期限切れキーへの同時流入がそのままAPIへの同時取得になる。
- 内部API読み取りは、通信失敗（`fetch` の `TypeError`）と5xxに限り**1回だけ**再試行する。`API_INTERNAL_TIMEOUT_MS` は1回分ではなく呼び出し全体の予算とし、待機後に予算が残らない場合は再試行せず元のエラーを返す。自前のタイムアウトによる中断（`AbortError`）と、本文がJSONでない場合（`SyntaxError`）は再試行しない。401・403・404などの4xxはAPIが返した答えとして扱い、再試行しない。並列読み取りが同時刻に再試行を揃えないよう、待機時間にジッタを加える。
- 再試行の対象は、ページのスナップショットが使う単一リソースの読み取りだけとする。サイトマップが使う全ページ走査（`getAllOpportunities`、`getAllIndexableCompanies`）は、部分失敗を503＋`Retry-After`で答える設計がすでにあるため再試行しない。ブロッキング再取得には代替のスナップショットが存在しないため、この限定した範囲でだけ瞬間的な接続断が5xxになるのを防ぐ。
- ADR-0016のその他の判断（metadataと本文の同一スナップショット共有、`no-store` fetch、詳細404の `null` キャッシュ、関連募集の best-effort、`htmlLimitedBots`、サイトマップ503、カテゴリallowlist、旧URL転送）は変更しない。

## Consequences

1時間以上訪問がないURLでも、APIが正常なら最初のアクセスから正しいページとmetadataを返す。期限の延長・自動リロード・エラーの握りつぶしを行わないため、鮮度の上限は従来どおり1時間のままである。

代償として、期限切れキーへの最初のリクエストはAPI応答を待つぶん遅くなる。APIが停止していれば、そのURLは古い画面ではなく5xxになる（ADR-0016の意図どおり）。したがってAPI応答時間と5xxの監視は引き続き必要である。in-flight マップはプロセス単位のため、複数インスタンス構成では同時取得がインスタンス数まで増える。

次の3点は運用上の前提として記録する。

- `unstable_cache` のキーはコールバックのソースを含むため、この変更のデプロイで3つのキー空間がすべて入れ替わる。デプロイ直後は各URLの初回アクセスがブロッキング取得になり、旧エントリは参照されなくなる。
- 描画中に例外が出たリクエストはNext.jsが再描画するため、失敗する画面表示1回あたりの上流呼び出しは「描画2回×試行2回」で最大4回になる（変更前は2回）。APIが停止しているときだけ発生し、いずれも即座に失敗する。
- PPR／`cacheComponents` を有効にすると、`unstable_cache` が期限切れエントリを再検証なしで返す経路が生まれ、相乗り先がなくなる。有効化する場合はこの判断を再検討する。
